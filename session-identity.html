Session & visit identity

How does Umami know two page views belong to the same visitor without a cookie? It recomputes the same UUID from the same inputs on every hit — and this page lets you recompute one yourself.

1 · The hash 2 · Recompute it 3 · Time-zone trap 4 · Visits 5 · Identified users 6 · Consequences

1A session id is a v5 UUID of who you look like this month

Five inputs go into one SHA-512, salted with the app secret; the hex digest is then the name of a v5 UUID in the DNS namespace.

export function hash(...args: string[]) {
  return crypto.createHash(HASH_ALGO).update(args.join('')).digest(HASH_ENCODING); // sha512, hex
}

export function secret() {
  return hash(process.env.APP_SECRET || process.env.DATABASE_URL);
}

export function uuid(...args: any) {
  if (args.length) {
    return v5(hash(...args, secret()), v5.DNS);
  }

  return process.env.USE_UUIDV7 ? v7() : v4();
}

export function getSalt(saltRotation: string, createdAt: Date): string {
  return hash(
    (saltRotation === 'day' ? startOfDay : saltRotation === 'week' ? startOfWeek : startOfMonth)(
      createdAt,
    ).toUTCString(),
  );
}

🔑

The session id is never stored on the client and never looked up. It is recomputed from scratch on every hit. Two hits get the same session exactly when all six inputs above are byte-identical — which is why the same person shows up as a new session on the first of the month.

3The month boundary is the server's local midnight, not UTC's

startOfMonth, startOfWeek and startOfHour from date-fns work in the Node process's local time zone; only the resulting instant is formatted as UTC.

⚠️

Same hit, three servers, three session ids. The fixture instant 2024-01-01 00:00 UTC is still December 31 in Los Angeles, so a server with TZ=America/Los_Angeles salts with Fri, 01 Dec 2023 08:00:00 GMT and returns 8f2bdb44-3b1e-53cd-b274-f611eea5a107. On Asia/Kolkata (+05:30) even the hour bucket shifts by 30 minutes, changing the visit id too. Pick the time zone in the widget to see it. Running two app instances with different TZ settings behind one load balancer splits sessions at every boundary.

The Dockerfile sets no TZ, so the official image salts on UTC boundaries; a bare-metal install inherits the host's zone. startOfWeek uses date-fns' default week start, Sunday.

4A visit is the session plus the hour, pinned by the cache token for up to 30 minutes

visit_id = uuid(sessionId, hash(startOfHour(createdAt).toUTCString())) — but the tracker's cache token can keep an older visit id alive.

No cache token
Visit id is derived from the current hour. Two hits at 10:59 and 11:01 land in different visits.
uuid(sessionId, visitSalt)
Cache token present, under 30 minutes old
visitId and iat come from the token — so the 10:59 visit continues at 11:01 for a tracker that kept its token.
cache?.visitId · cache?.iat
Token iat older than 1800 s
A new visit id is derived from the current hour and iat resets. Skipped when the payload carries an explicit timestamp (imports, backfills).
!timestamp && now - iat > 1800
Session drift
If the token's sessionId differs from the recomputed one (new month, new IP), a fresh visit starts and, on Postgres, the session row is (re)created.
sessionDrift · shouldEnsureSession
⚠️

The 30 minutes are a cap, not an inactivity timeout. let iat = cache?.iat || now carries the token's iat forward unchanged on every response, so it records when the visit's token was first issued. An active visitor is rolled into a "new" visit 30 minutes after the first hit — and because that new id is re-derived from the current hour, it equals the old id if the clock hour has not changed. Tested by "regenerates the visit when the cached iat is older than 30 minutes" in route.test.ts.

The browser side of the token is covered in The tracker script.

5Identifying a user forks a new session on purpose

distinctId is part of the hash, so umami.identify('user-1') moves that visitor into a different session from the anonymous one sharing their IP and user agent.

The test "uses distinct IDs to separate sessions with the same client fingerprint" asserts exactly that, and "normalizes distinct IDs before calculating the session ID" asserts that two ids sharing their first 50 characters collapse to one session — truncateString(id, 50) runs before hashing. Try a 51-character id in the widget. To connect the anonymous and identified sessions, the identify branch writes session_link (website_id, distinct_id, session_id) and updates the session's distinct_id (see data model).
