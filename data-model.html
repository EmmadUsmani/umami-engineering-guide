Data model

What are Umami's nouns, how do they relate, and which table does every chart read? Short answer: almost everything you see in the dashboard is computed from one wide, append-only table — website_event.

Read website_event first. Every dashboard number — page views, visitors, visits, channels, funnels — is a query over that one table. Sessions and visits are just ids on its rows; on ClickHouse even the session's attributes live there.

1The 26 models fall into four domains, and only one of them is hot

Tenancy and saved-analysis tables are small and edited by people; the write path is written by every visitor on every page view.

A website is owned by either a user or a team (user_id / team_id, both nullable), and soft-deleted through deleted_at. link and pixel follow the same ownership shape and add a unique slug. share is polymorphic: entity_id plus an integer share_type, with no foreign key.

3The spine is website → session → website_event, and most of its arrows are not foreign keys

Solid lines are Prisma relations; dashed lines are bare id columns with no relation declared. With relationMode = "prisma", none of them is a database-level foreign key.

Core of prisma/schema.prisma. Dashed = id column only. Purple = tenancy, teal-blue = tracked entity, blue = session side, green = event side.
datasource db {
  provider     = "postgresql"
  relationMode = "prisma"
}

model WebsiteEvent {
  id        String @id() @map("event_id") @db.Uuid
  websiteId String @map("website_id") @db.Uuid   // no relation field → no join via Prisma
  sessionId String @map("session_id") @db.Uuid
  visitId   String @map("visit_id") @db.Uuid    // not a table — just a derived id
  ...
  session   Session @relation(fields: [sessionId], references: [id])
}
⚠️

Joins are by convention, not constraint. WebsiteEvent declares no relation to Website, and Session declares none to Website either, so prisma.websiteEvent.findMany({ include: { website: true } }) does not exist. Analytics code joins on website_id in raw SQL instead (src/queries/sql/).

visit_id is not a table: it is a deterministic UUID derived from the session id and the hour (see Session & visit identity). session_link records every (website, distinct id, session) triple seen by an identify call so a logged-in user's anonymous sessions can be stitched together.

5Custom data is stored as typed key/value rows, one per property

umami.track('signup', { plan: 'pro' }) becomes one website_event row plus one event_data row per key.

event_data
Keyed by website_event_id; data_key plus exactly one of string_value / number_value (Decimal(19,4)) / date_value, tagged by data_type.
session_data
Written by identify calls; unique on (session_id, data_key), so a later identify overwrites a key.
data_type
1 string · 2 number · 3 boolean · 4 date · 5 array (DATA_TYPE in src/lib/constants.ts).
revenue
Written alongside event_data on Postgres when the event data has revenue > 0 and a currency (src/queries/sql/events/saveEvent.ts). On ClickHouse it is a materialized view, website_revenue_mv.
