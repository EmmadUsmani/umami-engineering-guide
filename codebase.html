Codebase overview

Where does the code live, what does the build actually do, and which commands will you run in your first week? Umami is a single pnpm workspace: one Next.js app at the root plus two publishable packages.

🔑

Follow the three trees: a src/app/api/…/route.ts handler validates and authorises, a src/queries/ module talks to the database, and src/lib/ holds everything in between. Almost every change touches exactly those three places.

1Routes, queries and libraries are three sibling trees under src/

The App Router's route groups — (main), (collect), (compat) — organise files without changing URLs.

umami/
├── prisma/
│   ├── schema.prisma            # 26 models — the Postgres source of truth
│   └── migrations/              # 01_init … 26_add_api_key
├── db/clickhouse/
│   ├── schema.sql               # 10 tables + 4 materialized views
│   └── migrations/              # 14 ClickHouse migrations
├── src/
│   ├── app/                     # Next.js App Router: pages AND route handlers
│   │   ├── (main)/              # signed-in UI: websites, boards, links, pixels, settings, admin
│   │   ├── (collect)/           # q/[slug] short links, p/[slug] pixels
│   │   ├── (compat)/            # legacy report endpoints
│   │   ├── api/                 # 135 route.ts files — send, websites, auth, teams…
│   │   ├── mcp/                 # MCP endpoint (MCP_ENABLED=1)
│   │   └── share/[slug]/        # public share pages
│   ├── tracker/index.ts         # browser tracker → public/script.js
│   ├── recorder/index.js        # session-replay recorder → public/recorder.js
│   ├── lib/                     # crypto, auth, db switch, detect, clickhouse, kafka, redis
│   ├── permissions/             # canViewWebsite & friends
│   ├── queries/
│   │   ├── prisma/              # 15 CRUD modules
│   │   └── sql/                 # 81 analytics modules (Postgres + ClickHouse bodies)
│   ├── components/              # React UI, hooks (TanStack Query), charts
│   └── store/                   # zustand stores
├── packages/
│   ├── api-client/              # @umami/api-client, generated from OpenAPI
│   └── mcp/                     # @umami/mcp, standalone MCP server
├── scripts/                     # build-geo, check-db, seed-data, OpenAPI generators
├── tests/
│   ├── api/                     # Playwright API suite, runs on Postgres AND ClickHouse
│   └── e2e/                     # Playwright browser suite
└── next.config.ts               # rewrites: tracker name, collect endpoint, API_URL

Rule of thumb: an endpoint is a thin route.ts that calls parseRequest, a src/permissions/ check, and one function from src/queries/. Business logic that is not a query lives in src/lib/.

3pnpm build is eight steps, and two of them write files the app serves

The build script is an npm-run-all chain; knowing the order explains most "works in dev, breaks in build" surprises.

check:env
Fails fast on missing required environment.
scripts/check-env.js
build:db
prisma generate into src/generated/prisma, then a bundled client.
scripts/build-prisma-client.js
check:db
Connects and applies migrations — this is where a fresh install gets its tables and the admin user inserted by prisma/migrations/01_init.
scripts/check-db.js
build:tracker
Type-checks and rolls up src/tracker/index.ts to public/script.js, baking in COLLECT_API_HOST/COLLECT_API_ENDPOINT at build time.
rollup.tracker.config.js
build:recorder
src/recorder/index.js → public/recorder.js.
rollup.recorder.config.js
build:geo
Fetches the GeoLite2 City database into geo/.
scripts/build-geo.js
build:openapi · build:packages
Generates the OpenAPI document and the typed API client, then builds packages/*.
scripts/generate-openapi.ts · generate-api-client.ts
build:app
next build --turbo.
next.config.ts
ℹ️

Because the collect endpoint is baked into public/script.js at build time, changing COLLECT_API_ENDPOINT needs a rebuild of the tracker, not just a restart. next.config.ts separately rewrites that path to /api/send.

5The API suite is the only thing that checks both backends agree

122 *.test.ts(x) files exist under src/, tests/ and packages/, but most unit tests mock the database and assert on SQL text.

The Playwright suite in tests/api/ ingests a fixed cast of personas (alice … frank in tests/api/seed/dataset.ts) through the real /api/send and asserts on real query results, on whichever backend scripts/test-api.ts started. That makes it the strongest evidence for any "the dashboard shows X" claim — Channel attribution seeds its widget from it. CI (.github/workflows/ci.yml) runs OpenAPI checks, pnpm test, package tests and a full build.
