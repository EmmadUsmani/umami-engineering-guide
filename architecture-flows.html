Architecture · flows

What actually happens, file by file, when a visitor loads a page, clicks a short link, an admin logs in, a dashboard renders, or a stranger opens a public share link?

🔑

Every website_event write funnels through POST in src/app/api/send/route.ts. Short links, pixels and batch uploads call that same function in-process rather than re-implementing it, so a change there changes every ingest path.

1A page view is one unauthenticated POST that writes one row

The browser half lives in src/tracker/index.ts; the server half in src/app/api/send/route.ts.

Tracker initialises
Reads data-website-id and friends from its own <script> tag; when the document is complete, auto-tracks a page view and hooks history.pushState/replaceState.
src/tracker/index.ts · init() → track()
Opt-out checks, then POST
Skips if localStorage['umami.disabled'], a non-matching data-domains, or Do-Not-Track (when data-do-not-track is set). Otherwise fetch with keepalive: true and the cached token.
trackingDisabled() · send()
Validate and authenticate nothing
parseRequest(request, schema, { skipAuth: true }). The zod schema requires exactly one of website, link, pixel and rejects event names starting with = + - @ (CSV-injection guard).
src/lib/request.ts
Trust the cache token or look the website up
A valid x-umami-cache JWT of type cache skips fetchWebsite; otherwise an unknown or soft-deleted website returns 400.
parseToken · src/lib/load.ts fetchWebsite
Client info, bots, blocked IPs
getClientInfo parses UA and geo; isbot(userAgent) returns {beep: 'boop'} with status 200 (unless DISABLE_BOT_CHECK); IGNORE_IP matches (exact or CIDR) return 403.
src/lib/detect.ts
Derive session and visit
Deterministic UUIDs from website, IP, UA, a month salt and the hour — the subject of Session & visit identity. On Postgres a session row is created when there is no cached session.
src/lib/crypto.ts uuid · getSalt
Split the URL and referrer, save
Pulls utm_* and six click ids (gclid, fbclid, msclkid, ttclid, li_fat_id, twclid) from the landing URL; drops the referrer domain on self-referrals; saveEvent writes via Prisma, ClickHouse insert, or Kafka.
src/queries/sql/events/saveEvent.ts
Return a fresh cache token
The response carries a JWT with websiteId, sessionId, visitId, iat; the tracker sends it back on the next hit.
createToken(…, secret())
POST /api/send
Content-Type: application/json
x-umami-cache: <JWT from the previous response, if any>

{ "type": "event",
  "payload": { "website": "<uuid>", "hostname": "example.test", "url": "/pricing",
               "referrer": "https://t.co/abc123", "title": "Pricing",
               "screen": "1920x1080", "language": "en-US" } }

→ 200 { "cache": "<JWT>", "sessionId": "<uuid v5>", "visitId": "<uuid v5>" }

2A short-link click re-enters the collection route in-process, then redirects

src/app/(collect)/q/[slug]/route.ts does not duplicate any collection logic — it builds a synthetic request and calls POST from api/send/route.ts directly.

const payload = {
  type: 'event',
  payload: {
    link: link.id,
    url: request.url,
    referrer: request.headers.get('referer') || undefined,
  },
};

const req = new Request(request.url, {
  method: 'POST',
  headers: request.headers,
  body: JSON.stringify(payload),
});

await POST(req);

return NextResponse.redirect(link.url);

The link lookup is cached in Redis for 24 h as link:{slug} when Redis is on. The event is saved with event_type = 3 and website_id set to the link's id — links and pixels share the event table with websites. Pixels (p/[slug]) follow the same pattern with event_type = 4. src/app/api/batch/route.ts uses the same trick to replay an array of payloads through send.POST.

ℹ️

The redirect waits for await POST(req), so a slow database adds latency to every short-link click.

3Login returns a token bound to the password hash

src/app/api/auth/login/route.ts issues one of two token shapes depending on whether Redis is configured.

Check credentials
getUserByUsername then checkPassword (bcrypt hash in user.password).
src/lib/password.ts
2FA short-circuit
If two_factor_auth.is_enabled (and not in cloud mode), respond {requiresTwoFactor: true, partialToken}. checkAuth refuses that token everywhere except the 2FA verify step.
PARTIAL_AUTH_TOKEN_TYPE
Mint the session token
pwd = hash(user.password). With Redis: saveAuth stores {userId, role, pwd} under auth:<random> and returns that key, signed. Without: a self-contained secure token with the same fields.
src/lib/auth.ts saveAuth · src/lib/jwt.ts createSecureToken
Every later request
checkAuth reloads the user and compares hash(user.password) with pwd; changing the password invalidates every older token.
src/lib/auth.ts checkAuth

4A dashboard tile is two queries: the period and the comparison period

src/app/api/websites/[websiteId]/stats/route.ts is the template for nearly every analytics endpoint.

Parse + authenticate
parseRequest(request, withDateRange({ ...filterParams })) validates dates and filters and runs checkAuth.
src/lib/schema.ts · src/lib/request.ts
Authorise
canViewWebsiteSection(auth, websiteId, ['overview', 'compare']): admins pass; share tokens pass for their own entity ids; otherwise the user must own the website or belong to its team.
src/permissions/website.ts
Query twice
getWebsiteStats for the range, then again for getCompareDate(filters.compare ?? 'prev', …); both go through runQuery.
src/queries/sql/getWebsiteStats.ts · src/lib/date.ts
Respond
json({ ...data, comparison }); the React client renders via TanStack Query hooks in src/components/hooks/queries/.
src/lib/response.ts

5A public share link is a scoped token, not a login

src/app/api/share/[slug]/route.ts trades a share slug for a signed token limited to the shared website, link, pixel or board.

Resolve the slug
getShareByCode(slug) finds the share row; its share_type and entity_id say what is shared.
src/queries/prisma/share.ts
Mint a share token
createToken({ type: 'share', websiteId | linkId | … }, secret()); the share page (src/app/share/[slug]/) keeps it client-side.
SHARE_TOKEN_TYPE
Call the normal API
Requests carry x-umami-share-token and x-umami-share-context; checkAuth returns authType: 'share' only when both are present.
SHARE_TOKEN_HEADER · SHARE_CONTEXT_HEADER
⚠️

The cache token and share token are signed with the same secret. parseShareToken therefore rejects any token whose type is not 'share' — otherwise the /api/send cache token (which carries a websiteId) could be replayed for read access. Keep that check if you add a token type.
